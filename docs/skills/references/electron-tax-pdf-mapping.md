# 电子税务局 PDF ↔ 拦截规则映射（DescribeSbmxxqcx）

## 背景
用户每月从税局下载增值税申报表 PDF（如 `2026年3月海盛和蓝色海洋科技（青岛）有限公司--增值税及附加税费申报表（一般纳税人适用）.pdf`），需要把 PDF 数值做成拦截 mock 规则（模拟税局系统返回该报表）。

## 接口指纹
- pattern（统一）：`.../szc/szzh/sjswszzh/zhcx/v1/DescribeSbmxxqcx`
- bodyPattern 两行，靠 reportIdList 区分报表：
  ```
  "reportIdList":["BDA0610606"]
  "skssqq":"2026-03-01"
  ```
- skssqq = 税款所属期起（月份随规则变：2026-06-01 等）

## PDF 页面 ↔ 后缀 ↔ reportId 对应
| 后缀 | PDF 页 | 报表名称 | reportIdList |
|------|--------|----------|--------------|
| -01 | 第 1 页 | 增值税及附加税费申报表（一般纳税人适用） | BDA0610606 |
| -02 | 第 2 页 | 附列资料（一）本期销售情况明细 | BDA0610607 |
| -03 | 第 3 页 | 附列资料（二）本期进项税额明细 | BDA0610608 |
| -06 | 第 6 页 | 附列资料（五）附加税费情况表 | BDA0611153 |

PDF 第 4/5/7 页（附列资料三/四、减免税明细表）json 里没有对应规则，不用管。
（同接口还有 DescribeSbmxcx2 = 合计/total 类规则，reportId 不同，本会话未深入。）

## 响应结构
```json
{ "Response": { "RequestId": "随机串", "Error": null, "Data": "<整页HTML>" } }
```
- Data = 报表 HTML（`<style id="report1_style">` 样式 + `<table>` 表格），数值与 PDF 逐格一致
- 响应长度约 17KB(06) ~ 39KB(02)，152~190 个数字单元格
- 生成新月份规则只需改：bodyPattern 的 skssqq 月份、HTML 内税款所属期（2026年3月1日至2026年3月31日）、填表日期（2026年4月20日，取自 PDF 页眉）、表格数值

## 两套公司规则
DescribeSbmxxqcx 同一月份有**两套 4 条**（数值不同，两家公司）：
- 无前缀（26.3-01/02/03/06）→ 蓝色海洋科技
- hsh/hxh 前缀（hsh-26.3-01…、hxh-26.3-06…）→ 海盛和食品
- 命名惯例：`{店铺}-{YY}年{M}月-{报表名}`，如 `蓝色海洋-26年3月-增值税及附加税费申报表`
- 报表名映射：-01 增值税及附加税费申报表 / -02 增值税及附加税费申报附列资料 / -03 增值税及附加税费申报附列资料（二）/ -06 附加税费情况表 / -total 合计

## 大坑
- **"仅导出启用"会过滤 disabled 规则**：蓝色海洋 26.3-02/03/06 在原始 0808 文件里 enabled=False，用户导出 154 条时被过滤 → 只看导出文件会误以为"只有 4 条"；核对两套完整性必须查原始 166 条文件（D:\Whale\chrome_url_interceptor\rules\txcs-interceptor-rules - 海盛和食品0808.json）。
- alias 匹配注意 (copy) 后缀：`hsh-24.12-01 (copy)` 等，改名/查找正则要容忍 `(?:\s*\(copy(?:\s*\d+)?\))?`。
- 年月格式：alias 是 26.3 / 26.03 混用（26.03-total），生成规则名统一 `26年3月`（月去前导零）。

## 数值替换核心算法（2026-08 验证通过，勿再用行匹配）
首版按"行标签匹配"（HTML <tr> 行 ↔ PDF 行文本）失败：合并单元格/竖排标题行（如"一、一般计税方法计税"被 pdftotext 拆成多行）导致大量行匹配不上（页2 只匹配 7/22）。**改用 difflib 序列对齐**，对三组数值序列：
- H3 = 26.3 基底规则 HTML 数值序列；P3 = 26.3 PDF 数值序列；P6 = 6 月 PDF 数值序列
- `h2p = align(H3, P3)`、`p2p = align(P3, P6)`；新值 `H6[i] = P6[p2p[h2p[i]]]`（无映射保持原值）
- align 用 `difflib.SequenceMatcher(None, fa, fb, autojunk=False).get_opcodes()`，**float 归一化比较**（`float(n.replace(',',''))`，否则 "500,691.60" vs "500,691.600000" 失配）；equal 段一一映射，replace 段按 min 长度对齐
- **自洽验证必跑**：用 P3 按 h2p 替换 H3 应全等（不一致=0），这是对齐正确性的唯一硬指标
- 提取正则：`\d{1,3}(?:,\d{3})*\.\d{2,6}`（支持 2~6 位小数）；HTML 提取前 `re.sub(r'\s+','',...)` 去全部空白（含 \r\n，见跨行陷阱）

## PDF/HTML 数值提取陷阱（都实际踩过）
- **跨行数字**：HTML 里 "500,691.600\r\n000"（td 内换行）→ 正则匹配失败导致该单元格漏提取、后续全部错位；先去掉所有空白再提取
- **序列长度天然不一致，严禁按序替换**：页1 PDF 121 vs HTML 119；页6 PDF 48 vs HTML 51(52)——减免性质代码列 PDF 为空而 HTML 有 0.00，差 1~3 个；6 月 PDF 页1 只有 120 个（又差 1）。必须走序列对齐
- **页6 合计行格式特殊**：26.3 是 "500,691.600000"（6 位小数且跨行）、6 月是 "21623.34"（无千分位）；序列对齐后合计行仍可能错位（残留下月值 10,013.83）→ **合计行手工按列修正**：10 个单元格 = `['21,623.34','0.00','0.00','0.00','864.93','0.00','432.47','0.00','0.00','432.46']`（第 4 个 0.00 是减免码列）。td 内容替换用 `re.sub(r'>[\s\S]*?<', '>'+v+'<', raw, count=1)`（整段替换，跨行文本也能命中）
- **PDF 原文不一致照抄**：6 月合计行 PDF 原文就是 432.47 与 432.46 并存（税局系统四舍五入差异），不要"修正"成一致
- **填表日期**：-01 取 6 月 PDF 页1 页眉（如 2026年7月15日）；-02/-03 PDF 页眉没有 → 按 3 月版顺延（4月13 → 7月13）；-03 日期格式带前导零（2026年04月13日 → 2026年07月13日），DATE_REPL 列表两种格式都要写
- 替换顺序：先数值（re.sub 带计数器逐格替换）再日期（DATE_REPL replace 列表）；替换后检查 `2026年3月`/`2026年04月` 残留 = False

## 生成后验证抽查（每条规则）
页1 销售额/销项税额/应纳税额/本期应补(退)税额；页2 13%税率货物行、6%税率行；页3 认证相符专票、当期申报抵扣进项税额合计；页6 城建税/教育/地方三行 + 合计——HTML 与 6 月 PDF 逐行对。完整工作流脚本见 `scripts/tax-pdf-to-rules.py`（pdftotext 两版 PDF + 基底规则文件 + 输出路径即用）。
